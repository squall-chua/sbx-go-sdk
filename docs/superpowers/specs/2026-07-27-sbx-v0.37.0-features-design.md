# Design: sbx v0.37.0 sync + v0.35.0 catch-up

- **Targets:** `sbx` / `sandboxd` v0.37.0 (daemon API `0.24.0`)
- **Supersedes pins from:** v0.35.0 (daemon API `0.22.0`)
- **Companion decisions:** [ADR 0003](../../adr/0003-reclaim-rest-paths-for-cp-unpublish-policy-list.md),
  [ADR 0004](../../adr/0004-version-alignment-is-a-development-time-gate.md)
- **Follow-on:** kit support is deliberately deferred to a second spec (see Non-goals)

## Background

The CLI moved v0.35.0 → v0.37.0 (there is no v0.36.0; the tag 404s, which is why the daemon API
jumped two minors at once). Re-running `dwarfgen` against the new binary produced a
**byte-identical** `internal/api/types_gen.go` apart from known generator artifacts, and the whole
existing SDK surface passes `internal/integration` unchanged. The only rename is internal:
`SandboxStatus` → `SandboxInfoStatus`, which does not affect JSON.

So this is not a repair job. It is three things:

1. **Three REST paths the SDK had written off now work**, so three shell-outs can go.
2. **v0.37.0 adds real features** — a shared skills store, `policy check`, `-p/--publish` at create.
3. **The v0.35.0 sync silently missed several v0.35.0 features.** An audit against the published
   release notes found `policy check`, `policy inspect`, `secret import`, `rm --force` and
   `sbx inspect` all shipped in v0.35.0 and none of them landed in the SDK. That audit gap is
   itself addressed here, by a coverage document wired into the drift gate.

A downstream consumer, `sbx-swarm-node`, pins `sbx-go-sdk v0.1.8` and integrates through a single
file (`internal/sandbox/sdkbackend.go`). **It is already broken against v0.37.0**, reproduced with a
throwaway module on the same pin:

```
SDK pinned: ClientVersion=v0.35.0 TestedAPIVersion=0.22.0
strict New()  -> err=incompatible sbx/daemon version  incompatible=true
lenient New() -> err=<nil>
live daemon   -> version=v0.37.0 api_version=0.24.0
```

Source compatibility for that consumer is therefore a **constraint on this work, not a preference**.
Every signature in this spec is chosen so `sdkbackend.go` keeps compiling untouched.

## Scope

| Area | Change |
|---|---|
| `sandbox` | `CopyFrom` → REST; `UnpublishPort` → REST; `WithPublish`; `Remove` + `WithForce` |
| `policy` | `Check` → `Authorization`; `InspectRaw`; `List` → REST |
| `secret` | `SetToken`; `SetRegistry`; `Import`; `ImportAll` |
| `skillstore` | new package: `Import` |
| `ssh` | `Setup` path fix + three doc corrections |
| `client` | deprecate `WithStrictVersion` and `CheckVersion` |
| `internal/untar` | new: confined tar extraction |
| `internal/cli` | new `CaptureStdin` — `Capture` cannot feed the child's stdin |
| docs | coverage table + drift-gate hook; glossary already updated |

Version pins (`client.ClientVersion` → `v0.37.0`, `TestedAPIVersion` → `0.24.0`) and the doc refresh
are already applied in the working tree and land in the same commit series as this spec, ahead of the
code changes it describes.

## Verified facts this design rests on

Everything below was confirmed against a live v0.37.0 daemon, not inferred. Query parameter names
came from DWARF (`GetFileParams`, `ListNetworkPolicyRulesParams`, `DeleteSandboxParams`) after an
initial round of guessed names (`follow_link`, `followLink`) produced false negatives.

| Endpoint | Confirmed behaviour |
|---|---|
| `GET /sandbox/{n}/files?path=&follow=` | `200 application/x-tar`; `path` required and absolute; `follow=true` resolves symlinks; tar rooted at `basename(path)`; entries owned `root/root` |
| `POST /sandbox/{n}/ports/unpublish` | body is a **bare `[]PortKey` array**, not `{"ports":…}`; `200 {"message":"unpublished N port key(s)"}` |
| `GET /policy/network/rules?type=all&sandbox=` | exact parity with `sbx policy ls <scope> --json`; **without `type=all` returns network rules only** (12 of 14) |
| `POST /policy/network/check` | `{type:"network", target, sandbox_id?}`; validates sandbox existence; `context` becomes `sandbox:<id>` |
| `DELETE /sandbox/{n}?force=` | `200`; plain delete already handles a *running* sandbox, `force` is for an *active session* |
| `POST /version` | **removed** — 404 on every verb, daemon reports `"release":true` |

## Migration 1 — `sandbox.CopyFrom` → REST

Signature unchanged: `CopyFrom(ctx, sandboxPath, localPath string, opts ...CopyOption) error`.

Implementation: `GET /sandbox/{name}/files?path=<abs>[&follow=true]`, then extract via
`internal/untar`. `WithFollowSymlinks()` maps to `follow=true`. `CopyTo` is untouched.

Placement rule, matching `sbx cp`: the tar is rooted at `basename(path)`, so when the destination
does not exist, extract into a staging directory beside it and rename `basename` → destination; when
the destination already exists as a directory, extract directly into it so the source lands inside.

**`CopyFrom` auto-starts a stopped sandbox** before the request. `sbx cp` prints
`Sandbox … started successfully` and succeeds, while `GET /files` answers
`409 sandbox is not running`. Auto-starting is required for parity and is deliberately unlike
`exec`, which needs `WithAutoStart()` — see ADR 0003.

### Validation already performed

A prototype extractor was diffed against `sbx cp` across 15 cases — files; directories; modes 0755
and 0640; file and directory symlinks with and without `-L`; a `:ro` workspace; a missing path; and
hostile symlinks — comparing path, type, mode, size, link target, ownership and contents.
**14 of 15 matched exactly.** The single divergence is intentional and in our favour: a failed
extraction into a non-existent destination leaves nothing behind, where `sbx cp` leaves a partial
tree. Two bugs were found and fixed during that exercise; both are recorded in ADR 0003.

## Migration 2 — `sandbox.UnpublishPort` → REST

Signature unchanged: `UnpublishPort(ctx, spec string) error`. A typed `Port` signature would read
better but breaks `sdkbackend.go:292`, which builds a spec string — rejected in ADR 0003.

Implementation: parse the CLI spec `[HOST_IP:]HOST_PORT:SANDBOX_PORT[/PROTOCOL]` into `PortKey`
values and `POST` a bare array. The only fiddly case is the IPv6 bracket form
`[::1]:18080:8080/tcp`; it gets a table test.

Publishing `18080:8080` on loopback creates **two** keys (`127.0.0.1` and `::1`). To preserve
today's ergonomics, when the parsed spec carries no host IP, read `GET /ports`, select every key
matching sandbox port and protocol, and unpublish that set — so one call still fully releases a port.

## Migration 3 — `policy.List` → REST

Signature unchanged: `List(ctx, c, scope string) ([]PolicyRule, error)`.

Implementation: `GET /policy/network/rules?type=all[&sandbox=<scope>]`. **`type=all` is mandatory and
load-bearing** — the endpoint defaults to network-only and omitting it silently drops filesystem
rules with no error and no drift signal. It is not configurable, precisely so that footgun cannot be
reached from the public API.

`ListRaw` keeps shelling out. `Profiles` is untouched — ADR 0002 already decided it stays raw until
real governance data exists, and `GET /policy/network/profiles` returns `{"profiles":[]}` here with
no `PolicyProfile` type in DWARF to model.

`PolicyRule.Origin`'s comment is corrected: it currently reads *"`local` or a remote-governance
source"* and misses `kit`, which is neither. Field name stays `Origin` (it is the JSON key);
the glossary term is *Source*.

## New — `policy.Check`

```go
func Check(ctx context.Context, c *client.Client, target string, opts ...CheckOption) (*Authorization, error)
func WithCheckSandbox(name string) CheckOption   // sets sandbox_id

type Authorization struct {
    Allowed       bool
    Action        string  // "net:connect:tcp"
    Context       string  // "global" | "sandbox:<id>"
    DenyKind      string  // "implicit" when nothing matched; empty when allowed
    Reason        string
    ResourceType  string  // "net:domain"
    ResourceValue string
    Rule          string  // deciding rule, when there is one
    Origin        string
    Target        string
    Governance    GovernanceStatus
}

// Mirrors sandboxapi.PolicyGovernanceStatus (DWARF); all but Active are optional.
type GovernanceStatus struct {
    Active                  bool
    Organization            string
    OrganizationUnavailable bool
    LastSyncedStatus        string
    LastSyncedMessage       string
}
```

`Authorization` rather than `CheckResult` because a rule's `Decision` (allow/deny, an input) and a
check's outcome (derived from all rules, an output) are different concepts, and `decision` was
naming both. *Authorize* is upstream's own verb. See the glossary entry.

`target` accepts a host, `host:port`, IP literal or URL, as the CLI does; a bare host is evaluated
at port 443 by the daemon. Unknown sandbox names surface the daemon's 404 through
`client.MapError`.

## New — `policy.InspectRaw`

```go
func InspectRaw(ctx context.Context, c *client.Client, selector string) (string, error)
```

Raw passthrough of `sbx policy inspect <policy-or-rule>`. There is no `--json`
(`ERROR: unknown flag: --json`) and no REST path, so typing it would mean parsing human-rendered
text that will drift. Matches the existing `ListRaw` pattern.

## New — `secret.SetToken` and `secret.SetRegistry`

The SDK currently **cannot create an ordinary secret** — it has `SetCustom`, `List`, `Remove`,
`RemoveCustom`, but no `Set`. This is the oldest gap found in the audit; it predates v0.32.0.

```go
func SetToken(ctx context.Context, c *client.Client, scope, service, token string, opts ...SetOption) error
func SetRegistry(ctx context.Context, c *client.Client, scope string, r RegistryCredential, opts ...SetOption) error
func WithOverwrite() SetOption   // --force

type RegistryCredential struct {
    Host     string // "ghcr.io"
    Username string // optional
    Password string
}
```

Two functions because their security properties genuinely differ, and the binary's own validation
strings show why:

```
--password-stdin and --username require --registry
--registry requires --password-stdin to read the password or token
```

`--password-stdin` is **registry-only**, so `SetRegistry` pipes the password in and never exposes it.

**Correction to an earlier assumption:** `internal/cli.Runner` has no stdin support for captured
output. `Capture(ctx, extraEnv []string, args ...string)`'s second parameter is *extra environment*,
not stdin, and `Capture` never assigns `cmd.Stdin`, so the child reads `/dev/null` and
`--password-stdin` would see EOF. `Inherit` does accept `Stdio{In: …}` but wires stdout/stderr to the
terminal and returns an exit code rather than captured output. `SetRegistry` therefore requires a new
runner method, `CaptureStdin(ctx, stdin io.Reader, extraEnv []string, args ...string)`, which is the
first task of the implementation plan.

A service secret has no secure path at all: the alternatives
are `--token` (value lands in `argv`, visible in the host process list) or the interactive
`Enter secret:` prompt, which runs through the bubbletea TUI and needs a real terminal. `SetToken`
is named so that exposure is unmissable at the call site, and its doc comment states it plainly.

`--oauth` is out of scope: interactive, and restricted to `openai`/global.

## New — `secret.Import` / `secret.ImportAll`, `skillstore.Import`

Both CLI commands prompt by default, so every wrapper must pass a non-interactive flag or hang.

```go
// secret
func Import(ctx context.Context, c *client.Client, service string, opts ...ImportOption) error
func ImportAll(ctx context.Context, c *client.Client, opts ...ImportOption) error
func WithDryRun() ImportOption

// skillstore
func Import(ctx context.Context, c *client.Client, opts ...ImportOption) error
func WithDryRun() ImportOption
```

`ImportAll` is named separately because `--all` sweeps **every detected credential env var on the
host** into the secret store; that blast radius belongs at the call site, not hidden behind a
default. `skillstore.Import` passes `--force` unconditionally — prompting is the only alternative,
and the CLI backs up each replaced folder first, so it is recoverable.

**Open item to resolve during implementation:** whether `secret import <service>` still prompts
without `--force`, or whether `--force` suppresses only the overwrite confirmation. The help text is
ambiguous and this was deliberately not tested against a live keychain holding real credentials.
Resolve with `--dry-run` first. The API shape above holds either way; only the flags passed change.

## New — `sandbox.WithPublish` and `Remove(WithForce())`

```go
func WithPublish(specs ...string) Option        // -p per spec, at create/run time
func (s *Sandbox) Remove(ctx context.Context, opts ...RemoveOption) error
func WithForce() RemoveOption                   // ?force=true
```

`Remove` stays variadic so `sb.Remove(ctx)` at `sdkbackend.go:168` keeps compiling. Plain delete
already handles a running sandbox; `force` is for one with an active session, which is now reachable
because `feature.ssh` defaults on. No `RemoveAll`: callers can loop over `List` in three lines and
keep their own error policy, which a library cannot choose well for them.

## `internal/untar`

```go
func Extract(r io.Reader, destDir string) error
```

`archive/tar` over the response body, every write confined by `os.Root`. Ownership from the tar is
ignored (entries are `root/root`; `sbx cp` writes as the calling user); mode bits are preserved,
re-applied with `Chmod` after create so `umask` cannot alter them.

**`os.Root` is necessary but not sufficient.** It confines writes and blocks traversal *through* an
escaping symlink, but still permits *creating* one. Symlink targets are therefore validated
explicitly: a relative target resolving outside the root is an error; an absolute target is allowed.
That asymmetry is not ours — it is exactly what `sbx cp` does (relative escape → exit 1, absolute
`-> /etc/passwd` → exit 0), and sandbox contents are agent-authored, so this is a real trust
boundary. See ADR 0003; do not remove the check believing `os.Root` covers it.

## Deprecations — `client.WithStrictVersion`, `client.CheckVersion`

Both keep working; both gain `// Deprecated:` markers. `CheckVersion` additionally returns an error
naming the removal of `POST /version` rather than surfacing a bare 404. Rationale, and the risk being
accepted, are in ADR 0004.

`sbx-swarm-node` needs a one-line change — drop `WithStrictVersion()` at `sdkbackend.go:35` — which
is tracked as downstream follow-up, not part of this spec.

## `ssh`

No REST surface exists; provisioning stays a shell-out. Four changes, three of them documentation:

1. `Setup` calls `sbx ssh setup`, an undocumented hidden alias. Point it at the documented
   `sbx setup ssh`; both accept `--alias` identically today.
2. `TargetFor`'s comment says *"With ssh.autoCreate (default true) … a target for any name is
   valid"*. The live default is **`false`**, so the conclusion is backwards. Fix it.
3. Note that `feature.ssh` now defaults to enabled, making `Enable` largely redundant.
4. Document that connecting auto-starts both the daemon and the target sandbox.

No `AcceptEnv` accessor: `settings.Get(ctx, c, "ssh.acceptEnv")` already returns it, and a wrapper
over a working generic call is surface for nothing. The setting is security-relevant — it allowlists
which client env vars reach the sandbox — so it gets documented rather than wrapped.

## Error handling

Unchanged from the established split. REST failures go through `client.MapError`; shell-out failures
return the runner error; JSON-shape drift returns `client.ErrUnexpectedFormat`. New REST calls add no
new sentinels. `internal/untar` returns plain wrapped errors — a rejected symlink is a hard failure,
matching `sbx cp`'s exit 1.

## Testing

**Unit**, using the existing fake-runner and fake-transport patterns:

- `untar` table tests: file, directory, nested tree, mode preservation, `root/root` ownership
  ignored, `../` path escape, relative escaping symlink, absolute symlink permitted, unsupported
  entry type.
- `UnpublishPort` spec parser: bare `PORT:PORT`, host IP, protocol suffix, IPv6 bracket form,
  malformed input.
- `policy.Check` request encoding and `Authorization` decoding for both allow and deny shapes.
- `secret.SetRegistry` asserts the password goes to **stdin** and never into the argument vector.
- `SetToken`, `Import`/`ImportAll`, `skillstore.Import` assert the exact argument vectors, including
  that a non-interactive flag is always present.

**Integration** (`//go:build integration`):

- `policy.Check` allow and deny against a live daemon, global and sandbox-scoped.
- `policy.List` returns filesystem rules as well as network — the regression test for the missing
  `type=all`.
- Extend the cp/ports smoke test to cover REST `CopyFrom` (file, directory, symlink with and without
  follow) and REST `UnpublishPort` releasing both address families.
- `CopyFrom` against a **stopped** sandbox, asserting the auto-start.
- `skillstore.Import` and `secret.ImportAll` exercised `--dry-run` only, so no host state changes.

## Docs

- `docs/sbx-version-coverage.md` — new. One flat table, one row per upstream feature since v0.32.0:
  feature, sbx version, daemon API, SDK symbol, status (*covered* / *gap* / *deferred* / *n/a*).
  Includes the audit's findings as explicit rows, among them `sbx inspect`'s extra fields (kits, auth
  mode, active sessions) which `api.SandboxInfo` structurally cannot report.
- `TestContract_VersionAlignment`'s failure message gains *"…and reconcile
  `docs/sbx-version-coverage.md` against the release notes"*. This is the mechanism that makes the
  document survive: it puts reading the release notes into the ritual that already fires on every
  upgrade. Without it the table rots, which is how the v0.35.0 gaps happened.
- README: new APIs, the deprecations, and the known-deviations list updated to say the three
  migrated operations no longer shell out.
- `CONTEXT.md` and ADRs 0003/0004 are already written.

## Non-goals / future

- **Kits — deferred to a dedicated spec.** `sbx kit add/inspect/pack/pull/push/validate` plus a
  `WithKit` create option. The SDK has zero kit support today despite kits gaining significant work
  in v0.34.0 and v0.35.0. Separated because nothing in it shares code with this spec, and because
  nothing about it has been verified live — folding unverified work into a verified spec would drag
  the whole thing down to the confidence of its weakest part.
- Typed `policy.Profiles` and typed `policy.Inspect` — nothing to model against.
- `--include-inactive` — cannot be verified without remote-governance data.
- `secret --oauth` — interactive.
- `CopyTo` migration — `PUT /files` exists; the shell-out works and rewriting buys nothing.
- `sbx diagnose` / `login` / `logout` — never wrapped, pre-date v0.32.0; recorded as gaps.
- Create-request fields the daemon accepts but the CLI cannot pass (`Environment`, `SecretsScope`,
  `PullPolicy`, `RootFilesystemSize`, `DindVolumeSize`, `EnableVirtiofsCache`, `Display`,
  `AgentOptions`, `BindingsPath`, `CredentialValues`) — unreachable while creation shells out.
- Proxy and virtiofs env vars (`DOCKER_SANDBOXES_PROXY`, `DOCKER_SANDBOXES_NO_PROXY`,
  `DOCKER_SANDBOXES_ENABLE_VIRTIOFS_CACHE`) — they work without SDK surface; documented only.
